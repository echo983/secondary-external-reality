# sdlpal 数据格式研究记录

来源：sdlpal 引擎源码（`global.h`/`global.c`/`map.h`/`map.c`/`palcommon.c`/`yj1.c`），对照用户自己合法拥有的游戏数据验证。

## 已验证、可以直接用

- **MKF 归档容器**（`mkf.ts`）：文件开头一个小端 uint32 给出头部总大小（= 4×(块数+1)），之后是每块的小端 uint32 偏移量数组，块 N 的字节范围是 `[offset[N], offset[N+1])`。
- **YJ1 压缩**（`yj1.ts`）：块内数据以 `"YJ_1"` 4字节签名开头，其后是哈夫曼树（叶子/内部节点标记 + 值字节）+ 分块压缩数据（哈夫曼编码字面量 + LZSS 回溯引用）。已对 `MAP.MKF` 全部 225 个非空块验证：解压后长度和块头声明的长度精确一致，抽查的瓦片值在 `map.h` 文档的位布局下解出的贴图序号合理。
- **`EVENTOBJECT`**（`eventObjects.ts`）：地图上一个"物体/角色"的放置记录——坐标 (x,y)、层号、精灵图编号、触发方式（`TRIGGERMODE`：靠近/触碰，近/中/远几档）、状态（隐藏/正常/阻挡）、以及两个脚本入口号（`wTriggerScript`/`wAutoScript`，只解出原始数字，不解析/复用它们指向的脚本内容）。存在 `SSS.MKF` 第 0 块，RAW（不经过 YJ1 解压），16 个 2 字节小端字段 = 32 字节一条。真实数据里 5332 条（上限 `MAX_EVENT_OBJECTS = 5500` 是整个游戏的量级，不是一个镇子的）。
- **`SCENE`**（`scenes.ts`）：场景记录——对应哪张地图（`wMapNum`）、进入/离开时执行哪段脚本（同样只解原始数字）、`wEventObjectIndex` 是**前缀和边界**（不是数量！场景 i 的事件物体范围是 `[rgScene[i-1].wEventObjectIndex, rgScene[i].wEventObjectIndex)`，来自 `scene.c` 的实际用法，不是字段注释直接写明的）。存在 `SSS.MKF` 第 1 块，RAW，4 个 2 字节小端字段 = 8 字节一条。真实数据 294 个槽位、292 个有效场景，边界值全程单调不减，最大边界值 5332 和 EventObject 实际总数精确一致——两块提取互相印证。

## 已找到定义、还没解析验证的结构

- **`OBJECT`/`OBJECT_DOS`**（`global.h`）：物品/魔法/敌人/玩家角色的系统记录（联合体，按类型 6~7 个 WORD 字段）。原以为在 `DATA.MKF`，实际上**这份表在 `SSS.MKF` 第 2 块**（`DATA.MKF` 存的是 `STORE`/`ENEMY`/`ENEMYTEAM`/`MAGIC`/`BATTLEFIELD`/`LEVELUPMAGIC_ALL` 这些更细分的表，按块号 0/1/2/4/5/6）。DOS 版和 WIN95 版字段数不一样（6 vs 7 个 WORD），这份游戏数据具体是哪个版本还没确认。
- **`SCRIPTENTRY`**：脚本字节码，操作码 + 3 个操作数，是 `EVENTOBJECT`/`SCENE` 里脚本入口号实际指向的内容——**明确不打算解析/复用**，这是这个项目要绕开的刚性预设演出逻辑。存在 `SSS.MKF` 第 4 块。

## 对这个项目的取舍（对应 `docs/VISION-first-experience-instance-v1.0.md` §3 的复用边界）

**要**：`MAP.MKF` 瓦片网格（地理骨架）；`SSS.MKF` 的 EventObject 坐标/精灵/触发方式（"这里有什么"的花名册，不要它挂的脚本）；`SSS.MKF` 的 Scene 表（场景↔地图的对应关系，划场景边界用）；`DATA.MKF` 的角色/物品名字（当人物设定种子）；`M.MSG` 台词文本（当性格/背景素材，不当脚本跑）。

**不要**：`SCRIPTENTRY` 字节码本身；任何触发后"具体演出了什么"的逻辑。

## 规模参考

整个游戏最多 300 场景、5500 事件物体——远超一个镇子的量级。下一步真要提取余杭镇内容时，需要先定位"哪些场景/地图编号属于余杭镇"，只挑那部分，不是整体导入。
