# 插入阶段：非技术人员演示准备 v1.0

日期：2026-08-25
性质：计划文档。**这不是四阶段成熟度模型（`docs/STATUS-four-stage-maturity-assessment-v1.0.md`）里的第几阶段**，是一个目的驱动、临时插入的阶段——目标是"能把已经做好的东西给不懂技术的人看，并且让对方感觉到这是个真实世界，不是聊天机器人"，跟"内核往正式内核/引擎方向推进"是两件不同的事。做完之后回到原来的阶段2/3序列，不改变那条主线的判断。

## 1. 背景

阶段1（内核可行性实验品）已收尾，阶段2边界工作四步已完成（见 `docs/STATUS-four-stage-maturity-assessment-v1.0.md`）。用户提出一个实际需求：想把卧室/走廊/客厅这部分**已经跑通、真实测试过**的内容，讲给非技术人员看。讨论中确认了三件事：

1. 内容范围：只用卧室/走廊/客厅现有内容，**不涉及仙剑村子**（那部分连自然语言链路都没有，是阶段3该做的事，不属于这次插入阶段）。
2. 核心目标不是"功能全不全"，是**让人感觉到这是个真实但小的世界，可以相对开放地用自然语言访问，区别于愚蠢的聊天机器人**——具体信号是：诚实的记忆衰减（不完美背诵也不瞎编）、独立的证言路径、对超出建模范围的问题诚实拒绝而不是编造、同一件事换着问答案始终一致。
3. 演示不能是"游客缆车"——不是主持人念一套固定脚本让对方跟着敲命令，是对方能相对自由地打字，主持人心里有数、在合适的时机引导对方看到关键信号。

## 2. 演示清单（demo 要让人看到什么）

1. 自由描述一个动作，走通——不是选菜单。
2. 写一张纸条并藏起来 → 聊点别的/走开 → 回来问自己还记不记得内容（诚实衰减）。
3. 问室友知不知道纸条内容（证言路径独立于自己的记忆，能找回来）。
4. 故意问一个超出建模范围的东西（诚实拒绝，不瞎编）。
5. 换着花样、换着顺序问同一件事，答案始终一致。

第2-5点现在都是**已经跑通、有真实模型测试覆盖的能力**，不需要新开发。真正需要准备的是下面三块。

## 3. 三块准备工作

### 3.1 开场文案 / 引导文字（小，可以先做）

现状（`src/ssh/textShell.ts`）：开场是"secondary external reality MVP / 输入 help 查看测试范围"，`help` 文案本身也过时了（还写着"门外空间尚未开放"，但走廊/客厅早就是真实建模的地方；完全没提移动、记忆回忆、证言这些后来加的能力）。这套开场把自己框成一个"测试工具"，跟"沉浸式真实世界"的演示目标正相反。

改动：把开场换成场景描述（"你在卧室里，床边坐着，桌上有把钥匙……"），不是能力清单——让人凭直觉知道自己在哪、大概能做什么，不主动推 `help`（保留 `help` 作为后备，但不作为默认引导）。同时更新 `help` 文案本身，把它修正到跟当前真实能力一致（走廊/客厅/移动/记忆/证言都要写进去），即使不作为默认展示，至少不能是错的。

### 3.2 针对"陌生人自由输入"的真实模型鲁棒性测试

现状：现有真实模型语料（`src/eval/`）是为了验收具体机制设计的（比如专门测记忆衰减、专门测证言），不是"一个不知道底层设计的人第一次接触会怎么打字"这种自然分布。这中间有真实差距——不知道薄弱点在哪，猜不出来，得跑一轮真实模型测试才知道。

改动：新增一组真实模型 live-eval 语料，专门模拟"第一次接触、不知道有隐藏边界的陌生人"会怎么描述这五个清单动作——更随意的措辞、更口语化、可能带犹豫或多余的话。跑真实模型，记录哪些措辞失败，按失败模式决定是修 `objectIntent.ts`/interaction IR 提示词，还是这次不修、只记录成已知风险（demo 时主持人自己避开）。

### 3.3 访问层

现状：只有 SSH，且要求本地生成密钥、密码文件、手动设一长串环境变量启动——非技术人员没法自己碰。

改动：待定，具体方案还没聊——常驻实例是肯定要的（不能演示前现场启动），入口方式（网页终端 vs. 你亲自帮对方开好会话 vs. 别的）需要单独讨论确定。这是运维/部署层面的活，不涉及内核代码改动。

## 4. 明确不做的事

- 不涉及仙剑村子内容——那需要阶段3的加载器/感知/移动系统 wiring，量级不同，不属于这次插入阶段。
- 不为了"看起来更完整"而新增功能——这次插入阶段是**包装和验证已有能力**，不是开发新能力（3.2 的测试如果发现真实bug会修，但不会因为"demo看起来更酷"而添加新机制）。
- 不改变阶段2/3序列本身的判断——这个插入阶段做完之后，`docs/STATUS-four-stage-maturity-assessment-v1.0.md` 记录的"下一步是阶段3"这个判断不受影响，只是往后挪了一小段时间做这件事。

## 5. 建议顺序

1. 开场文案 + `help` 文案更新——最小、独立、可以立刻做。
2. 陌生人自由输入的鲁棒性测试——需要先做完1（不然测试的还是过时的开场体验），跑完看结果再决定要不要修东西。
3. 访问层——可以跟1/2并行讨论方案，但落地部署可以放最后，因为不影响前两块的准备。

每一块各自验收、各自确认后再往下走，不合并成一次性大改动，跟阶段2那四步的节奏一致。
