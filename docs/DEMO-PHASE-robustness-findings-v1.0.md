# 演示准备插入阶段 · §3.2 鲁棒性测试发现记录 v1.0

日期：2026-08-25
依据：`docs/DEMO-PHASE-plan-v1.0.md` §3.2。新增了第4个人设 `demo-rehearsal-newcomer`（`src/eval/runHumanPersonaExplorationLiveEval.ts`），专门模拟不知道底层设计的陌生人自然地尝试演示清单的五个动作，跑真实模型，按实际发现逐条处理。

## 1. 修了的三个真实 bug

都用真实模型直接复现、修复后用真实模型端到端验证过，不是靠猜测：

1. **引号包裹的数字内容被拒绝**（`src/interactionIr/compiler.ts`）。有人自然地会给要写的内容加引号，比如"我把纸条写上'1234'"——两个语言工位都会把引号原样当成 mention 的一部分抄下来（这符合"mention 必须是原文精确连续片段"的设计），但数字校验没有跳过引号的能力，每次都被拒绝。真实模型复现：连续15轮里，几乎每种数字都试了一遍，全部因为这个原因失败。修复：`extractDigitLiteral` 在校验前尝试从 mention 中提取被引号包住的数字段，同时兼容"数字'1234'"这种引号前面还带描述词的情况，但只在数字唯一、无歧义时才采信。
2. **"下面/下"这个方位词从未被识别**（`src/world/referenceLexicon.ts`）。`LOCATIVE_SUFFIXES` 原来只认"里/里面"（inside）和"上/上面"（on），完全没有"下/下面"。有人自然地把"写纸条"和"藏到枕头下面"拆成两句话（用"然后"连接）时，第二句怎么都解析不出"枕头下面"指的是枕头。修复：把"下面/下"并入"inside"组——这和"藏到枕头下面"在这个内核里本来就是用 `contained_by` 建模的（跟"放进抽屉里"是同一个关系类型）是一致的。
3. **枕头在通用放置动作里不被当作有效容器**（`src/turn/objectTurn.ts`）。`worldSchema.ts` 早就允许枕头作为 `contained_by` 的宾语，但 `place`/`put_inside` 这个通用动作处理函数只认 `container: "true"` 这个属性，枕头没有这个属性（只有专门的原子操作 `write_and_hide` 单独处理了枕头，但这个操作在 interactionIr 的操作集里根本不存在）。结果是：只要不是用那句连 interactionIr 都无法生成的固定atomic短语，"藏到枕头下面"这个动作在实际生产链路里完全走不通。修复：给通用放置动作加上跟 schema 层同样的例外（`entityType === "pillow"`），并把响应措辞从"放进了"改成"放到...下面"，跟原来 write_and_hide 的措辞保持一致。

三个修复叠加后，端到端验证（拿笔→写→拿起纸条→藏到枕头下面）全部成功提交，真实模型全程无误。全量测试 215 个，214 通过（唯一失败是已知的 ssh-server.test.js SIGSEGV，无关）。

## 2. 不是 bug，但对演示很重要的发现

**写字本身不会让自己"知道"自己写了什么——必须专门读一遍。** 这是既有的、在 `docs/MVP-memory-recollection-design-v0.6.md` 里就写明的设计决定：`write` 操作只对目击的室友生成 acquired evidence，自己不会因为"写了"就自动获得对内容的认识证据；只有专门"读"一遍纸条才会。已有的记忆回忆真实测试语料（`runMemoryRecollectionSequenceLiveEval.ts`）本来就严格遵守这个顺序（写→读一遍→回忆），只是这次探针的人设一开始没有模拟这个顺序，写完就直接问"我刚才写了什么来着"，得到的是 `NO_ACQUIRED_EVIDENCE`（诚实的"你没有可查阅的证据"），而不是更有戏剧性的"记得→忘记"曲线。

**对演示的直接影响**：如果想让"诚实的记忆衰减"这个演示时刻真正有戏剧性（先能回忆起、过一会儿再问就诚实地说记不清），主持人或对方自己操作时，写完纸条后**必须先读一遍确认内容**，再走开、再问回忆——直接跳过这一步不是 bug，是会诚实地告诉你"没读过就不知道"，这本身也是这个系统"不瞎编"的另一种体现，但作为演示话术要提前心里有数，别让对方以为卡住了。

**遇到不确定的事，有人会反复问"我能不能……"而不是直接尝试。** 系统把这类问题正确分类成"能力询问"（不会被当成动作执行，也不会瞎编答案）——这是正确的设计（能力问答本来就明确列为阶段1"不补"的项之一），但意味着如果对方是这种探索风格，可能会在原地反复问、迟迟不进入实际操作。这不需要修，只是主持人需要知道：遇到这种情况可以顺势提示"你可以直接试试看"。

**内部实体 ID 不会泄漏给真实用户。** 探针里看到过 `"nightstand-1 has no direct location."` 这类带内部 ID 的英文报错，但那是因为探针直接调用 `BedroomSession.submit()`，绕过了真实 SSH 层。真实链路（`src/ssh/textShell.ts`）的兜底分支只有匹配到中文字符的报错才会原样展示，其余一律换成通用提示文案——验证过，不是需要修的问题。

## 3. 结论

§3.2 的鲁棒性测试目标已达成：不仅发现了薄弱点，三个真正卡住核心演示流程（写纸条）的 bug 已经修复并验证。剩下的两条"不是 bug 但要注意"的发现，建议下次和用户过一遍演示脚本时口头提醒，不需要代码改动。
