# MVP 放置语义与实体落地加固（v0.2.0）

日期：2026-08-23

## 人类测试暴露的问题

同一会话中，以下输入曾失败：

- `把钥匙放到抽屉里`：语言层保留了 `抽屉里`，但实体绑定只接受完整别名，无法把空间后缀与实体分开。
- `把钥匙放到抽屉`：实体绑定成功，但 `place` 只接受表面，不能根据抽屉的容器能力落地。
- `把钥匙放到床上`：同样因空间后缀而无法绑定；床在种子世界中也没有独立的 `surface=true` 标记。
- SSH 方向键产生的 ANSI CSI 字节会混入下一行世界输入。
- 双语言工位偶发把 `place` 与 `put_inside` 当成不同解释，或把祈使句 `拿起钥匙` 误判为能力询问。

## 结构性修复

1. 引用层新增结构化空间指代解析。`抽屉里` 被解析为实体 `drawer-1` 与关系提示 `inside`；`床上` 被解析为实体 `bed-1` 与关系提示 `on`。不在允许集合内的后缀（例如 `门外`）不会被截断成已有实体。
2. 编译层把实体 ID 与空间关系分别传给世界执行层；关系提示 `inside` 可把放置族编译为 `put_inside`。
3. 世界层按目的实体能力选择关系：容器产生 `contained_by`，表面或床产生 `located_on`。对象必须已被主体持有；可开容器必须处于打开状态。LLM 不决定这些事实与约束。
4. 共识层只把 `place` 与 `put_inside` 视作同一放置词汇族，仍严格比较目标和去向的原文片段。最终关系继续由机械空间解析和实体能力决定。
5. 语言工位加入祈使句与能力询问的最小对照，避免把未出现的“能不能/吗”补入输入。
6. SSH 文本层丢弃可跨数据块到达的 ANSI CSI 序列，避免方向键污染真实 ttd 输入。

没有把局部实体表加入 LLM 提示。实测分歧来自操作词汇和语用分类，而不是实体识别；实体目录继续只存在于可信绑定与世界层，保持语言工位无世界事实授权。
