# 阶段2 · PlaceGraph 邻接数据化设计 v1.0

日期：2026-08-24
依据：`docs/STAGE2-BOUNDARY-DEFINITION-v1.0.md` 第1项，四步实现顺序第3步。

## 1. 问题

`objectTurn.ts` 的 `PLACE_ADJACENCY` 是编译期 TypeScript 表，只覆盖卧室/走廊/客厅这条四节点线性链。`content-pipeline/sdlpal-import/output/part1-authored.pack` 已经带着 17 个地点、18 条人工标注的邻接边（`adjacent:` 字段），这次探针完全没加载它们——每个新地点集合都要手写 TS 表，是"内容污染内核"在结构层的重演。

## 2. 范围：只做数据表示，不重写现有 move 逻辑

`present_at` 那一步的先例是"加校验规则，故意不接入现有感知/移动逻辑"；这一步延续同样的收窄：

**做的事**：新增关系谓词 `adjacent_to`，让"两个地点相邻"可以表示成 `WorldCommitment`，从而可以被将来的内容加载器写入。这就解开了"地点邻接关系是硬编码，不是数据"这个具体缺口——加载器现在有地方放这份数据了。

**不做的事**：不把卧室/走廊/客厅现有的 `PLACE_ADJACENCY`/`move` 校验逻辑迁移成读取 `WorldCommitment`。原因：
1. 现在没有具体消费方需要 `move` 命令走真正的地点图——sdlpal 内容还完全没接自然语言链路（`docs/STATUS-four-stage-maturity-assessment-v1.0.md` §4 阶段4 部分已经写明"这份内容现在哪都接不进去"）。
2. 现有 `PLACE_ADJACENCY` 除了拓扑，还带着 `requiresOpenDoor` 这种边属性（哪条边需要哪扇门开着）——`adjacent_to` 这个简单谓词没有地方放这种边属性，真要做，需要专门设计一套"边可以带属性"的机制，属于超出这一步范围的新设计。
3. 卧室/走廊/客厅这条链路是全项目测试覆盖最密的既有功能之一（阶段1的核心验收对象），现在没有真实需要就重构它，风险收益不成比例——违反"可行优先于完备"。

这一步的产出是"邻接可以被声明为数据"这个能力本身，卧室 fixture 继续用它原来的硬编码表，两者暂时并存，互不冲突。

## 3. 设计

新增关系谓词 `adjacent_to`：
- **校验规则**：主语、宾语都必须是 `entityType === "place"`；主语不能等于宾语（防止一个地点声称和自己相邻这种明显错误的数据）。
- **对称性是约定，不是强制**：跟 pack 文件本身的约定一致（两个地点互为邻居时，各自的 `adjacent:` 字段都会列出对方——已经用真实数据验证过这份 pack 是完全对称的），也跟现有 `PLACE_ADJACENCY` 的写法一致（每个方向显式列出，不自动互推）。这一步不加自动双向断言的逻辑，是否对称由写入方自己保证，内核不检查、不强制。
- **不做环检测**：地点图允许环（比如三个地点互相连通形成三角形），这在真实地理里完全合理，不是错误。

## 4. 验收

- 正例：两个 place 之间 `adjacent_to` 关系断言成功，双向各自断言也成功（不互相冲突）。
- 反例：宾语不是 place 类型被拒绝；地点和自己 `adjacent_to` 被拒绝。
- 本地测试 + 全量回归，不涉及真实模型 live-eval（纯 schema/校验层改动，不触碰 `objectTurn.ts`/自然语言解析路径）。
